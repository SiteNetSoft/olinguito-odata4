# OData conformance audit — Olinguito at master `8df82f77a`

**Date:** 2026-08-20. **Source of the checklist:** [OData-Protocol] v4.01 OASIS Standard, 23 April 2020, section 13 (Conformance), items transcribed verbatim into six slices. **Subject:** the library (`lib/server-*`, `lib/client-*`) together with the reference service `lib/server-tecsvc`, judged as "can a service built on this library conform, and does tecsvc conform".

**Method:** each clause was checked against the code by reading the implementation, not by matching names. Verdicts are SUPPORTED / PARTIAL / MISSING / N-A / UNVERIFIED, each carrying `file.java:line` evidence or the name of a pinning test. N-A marks roll-up clauses ("MUST conform to the level below") and clauses that are a deployment or modelling decision rather than a library capability.

**Scope note:** this audit covers [OData-Protocol] section 13 only. It does not re-audit [OData-JSON] section 24 or [OData-CSDL] conformance, and it judges the code as of `8df82f77a` — the Tier 6 Wave 3 plan (`docs/superpowers/plans/2026-08-20-tier6-wave3.md`) is **not** implemented, so clauses it would close are marked "Wave 3 planned" in their notes.

### What the levels come to

- **OData 4.0 Minimal — reachable.** No MUST is missing. The two PARTIALs are tecsvc's, not the library's: server-driven paging is implemented but tecsvc applies it to two demo entity sets, and `If-Match` is not enforced on the `$ref` write paths (`ODataDispatcher.handleReferenceDispatching`), which is a genuine MUST gap for an updatable service.
- **OData 4.0 Intermediate — reachable, with one real MUST gap.** Item 4 (casting to a derived type) is only partly honored: entity-set and navigation-property casts work, casts inside `$filter` are crudely special-cased, and casts on bound functions answer 501.
- **OData 4.0 Advanced — not reachable today.** `$levels` (9.8) is refused outright by tecsvc, `$search` inside `$expand` (9.7) is parsed and dropped, cast-in-expand (9.3) is parsed and never consulted, and `$crossjoin` (15) parses and validates but has no dispatcher case. `any`/`all` (5) never evaluate against navigation-valued properties and `all` never evaluates at all.
- **OData 4.01 Minimal — not reachable today, and this is the audit's main finding.** Five MUST-level items fail: no `AsyncResult` header (3), system query options are not accepted without the `$` prefix (6), query-option/operator/function names are case-sensitive (7), strings are not cast to primitive types in URL key values (9a), and a parameter-less function import requires `()` (9c). Item 4 (prefixed and non-prefixed preference names) is partial — only `track-changes` accepts both spellings.
- **OData 4.01 Intermediate and Advanced — not reachable.** Nested options inside `$select` are not parsed at all (only `/`-path nesting), and `$compute` does not exist as a system query option — both MUST at Advanced.

### The seven changes that would move the needle most

1. **Case-insensitive query options, operators and function names** (4.01 Min item 7) — `SystemQueryOptionKind.get()` and `UriTokenizer.nextConstant` are case-sensitive.
2. **`$`-less system query options** (4.01 Min item 6) — `Parser.java:334` only routes names starting with `$`.
3. **`AsyncResult` header and the unwrapped monitor result** (4.0 Min 16/17, 4.01 Min 3) — already specified in the Wave 3 plan, Tasks 9 and 11.
4. **Nested options in `$select`** (4.01 Int 5/9, Adv 5) — `SelectParser` has no parenthesized-options grammar.
5. **`$compute`** (4.01 Adv 4) — exists only as an `$apply` transformation.
6. **`$levels`, `$search`-in-`$expand`, cast-in-expand** (4.0 Adv 9.3/9.7/9.8) — all three are parsed today and dropped at evaluation.
7. **`If-Match` on `$ref` writes** (4.0 Min 26) — a MUST for an updatable service, and a small fix.

`$apply` evaluation and JSON Batch, the two features that look largest, are **not** on this list: `$apply` is not named by any conformance clause, and JSON Batch is explicitly a MAY (4.0 Advanced item 11).
