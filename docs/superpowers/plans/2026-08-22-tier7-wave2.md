> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the remaining §13.2.1 clauses that live outside the URI parser, prove the whole level clause by clause, and only then let the service declare OData 4.01 conformance in `$metadata`.

**`divby` is not `div`.** [OData-URL] §5.1.1.2.5: it *"promotes both operands to decimal before computing the result, may yield a fractional result, and does not fail for divby zero, returning -INF, INF, or NaN depending on the sign of the left operand."* So it must not be folded into `arithmeticOperator`, whose integer path does `BigInteger.divide` (truncating) and throws on zero.

**A real bug sits next to this work:** `decimalArithmeticOperation` (`BinaryOperator.java:337`) reads `case DIV -> left.divide(left);` — dividing the left operand by *itself*, so decimal `div` always yields 1. Fix it to `left.divide(right, MathContext.DECIMAL128)` in the same task and pin it with a test; note it separately in the commit message, because it is a pre-existing defect and not part of the 4.01 work.

In `BinaryOperator`:

```java
  /**
   * Divides the left operand by the right one, promoting both to decimal, per [OData-URL] 5.1.1.2.5.
   * Unlike {@link #arithmeticOperator} with DIV this may yield a fractional result and never fails
   * for division by zero: it returns -INF, INF or NaN depending on the sign of the left operand.
   */
  public VisitorOperand divByOperator() throws ODataApplicationException {
    if (left.isNull() || right.isNull()) {
      return new TypedOperand(null, primDouble);
    }
    final BigDecimal leftValue = left.asTypedOperand().getTypedValue(BigDecimal.class);
    final BigDecimal rightValue = right.asTypedOperand().getTypedValue(BigDecimal.class);
    if (rightValue.signum() == 0) {
      final double result = leftValue.signum() == 0 ? Double.NaN :
          leftValue.signum() > 0 ? Double.POSITIVE_INFINITY : Double.NEGATIVE_INFINITY;
      return new TypedOperand(result, primDouble);
    }
    return new TypedOperand(leftValue.divide(rightValue, MathContext.DECIMAL128), primDecimal);
  }
```

Use the class's existing field names for the primitive type instances (`primDouble`, `primDecimal` or whatever it declares — check the top of the file) and its existing null-operand idiom. Add `import java.math.MathContext;`.

In `ExpressionVisitorImpl`, replace the 501 line with `case DIVBY -> binaryOperator.divByOperator();` and delete the Wave 1 comment about Wave 2.

Also fix the neighbouring bug: `case DIV -> left.divide(left);` becomes `case DIV -> left.divide(right, MathContext.DECIMAL128);`.
