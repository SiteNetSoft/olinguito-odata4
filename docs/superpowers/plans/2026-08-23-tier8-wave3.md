# Tier 8 Wave 3 — Evaluating the Options on a Selected Collection

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Evaluate the query options a `$select` item may carry on a collection-valued property — [OData-Protocol] §13.2.2 item 9 — replacing the blanket 501 Wave 2 left behind with real behavior wherever the evaluator can reach, and a narrower 501 where it cannot.

**Architecture:** One new tecsvc handler walks the select items that carry options and rewrites the matching property's value on each entity, before the entity-level options run. `$top`/`$skip`/`$count` are list operations on the property's value. `$filter`/`$orderby` are reachable on a **complex** collection, because `ExpressionVisitorImpl` already has a `ComplexValue` constructor; on a **primitive** collection they need `$it`, which tecsvc's visitor does not implement, so those stay 501.

**Tech Stack:** Java 17, Maven, JUnit 5 in `lib/**`, JUnit 4 via the vintage engine in `fit/`.

**Spec:** `docs/superpowers/specs/2026-08-22-tier8-design.md` (citations: `docs/superpowers/specs/2026-08-22-tier8-citations.md`)

## Scope, and what remains after this wave

Wave 2 closed §13.2.2 item 5, the level's last MUST, and left item 9's options parsing but answering 501. This wave evaluates them as far as the evaluator reaches.

**`$compute` (item 8) and the tier close-out move to Wave 4.** `$compute` is not the small option it looks like: it needs a `ComputeOption` in `server-api` (the existing `Compute` is an `ApplyItem`, the wrong hierarchy for a system query option), a parser, wiring into `Parser.parseUri` **before** `$filter`/`$orderby`/`$select` so a computed alias resolves in them, an evaluator, and — the part that makes it cross-module — the JSON serializer must write computed properties on a **closed** type, where `writeDynamicProperties` currently returns early (`ODataJsonSerializer:768`). That reaches the public serializer options. Wave 4 takes it, along with the §13.2.2/§13.1.2 re-audit and the `CLAUDE.md` record.

Also still open and recorded rather than fixed: the `$select`-versus-`$expand` half of §11.2.5.1's duplicate rule (Wave 2, Task 3).

```java
package org.sitenetsoft.olinguito.server.tecsvc.processor.queryoptions.options;

/**
 * Applies the query options a $select item carries to the value of the property it names
 * ([OData-Protocol] 11.2.5.1, conformance 13.2.2 item 9). These options act on a property's
 * collection value, unlike {@code ExpandSystemQueryOptionHandler}, which acts on an expanded
 * entity collection.
 */
public final class SelectOptionsHandler {

  private SelectOptionsHandler() {
    // Utility class, mirroring the other handlers in this package.
  }

  public static void applySelectOptions(final SelectOption selectOption,
      final EntityCollection entityCollection) throws ODataApplicationException {
    if (selectOption == null || entityCollection == null) {
      return;
    }
    for (final Entity entity : entityCollection.getEntities()) {
      applySelectOptions(selectOption, entity);
    }
  }

  public static void applySelectOptions(final SelectOption selectOption, final Entity entity)
      throws ODataApplicationException {
    if (selectOption == null || entity == null) {
      return;
    }
    for (final SelectItem item : selectOption.getSelectItems()) {
      final String propertyName = selectedPropertyName(item);
      if (propertyName == null) {
        continue;
      }
      final Property property = entity.getProperty(propertyName);
      if (property != null && property.isCollection()) {
        applyToValue(item, property);
      }
    }
  }

  /** @return the name of the property a select item names, or null when it names something else */
  private static String selectedPropertyName(final SelectItem item) {
    if (item.getResourcePath() == null) {
      return null;
    }
    final List<UriResource> parts = item.getResourcePath().getUriResourceParts();
    return parts.size() == 1 && parts.get(0) instanceof UriResourceProperty resourceProperty
        ? resourceProperty.getProperty().getName()
        : null;
  }

  private static void applyToValue(final SelectItem item, Property property)
      throws ODataApplicationException {
    List<Object> values = new ArrayList<>(property.asCollection());

    if (item.getSkipOption() != null) {
      final int skip = Math.min(item.getSkipOption().getValue(), values.size());
      values = new ArrayList<>(values.subList(skip, values.size()));
    }
    if (item.getTopOption() != null) {
      final int top = Math.min(item.getTopOption().getValue(), values.size());
      values = new ArrayList<>(values.subList(0, top));
    }

    property.setValue(property.getValueType(), values);
  }
}
```

```java
  /**
   * Keeps the complex values for which the expression evaluates to true. A collection of primitive
   * values cannot be filtered here: naming the item requires $it, which this service's expression
   * visitor does not implement, so those are refused in TechnicalProcessor.validateOptions.
   */
  private static List<Object> filterComplexValues(final List<Object> values, final FilterOption filter,
      final Edm edm) throws ODataApplicationException {
    final List<Object> result = new ArrayList<>();
    for (final Object value : values) {
      if (!(value instanceof ComplexValue complexValue)) {
        throw new ODataApplicationException("$filter is supported on collections of complex values only.",
            HttpStatusCode.NOT_IMPLEMENTED.getStatusCode(), Locale.ROOT);
      }
      final VisitorOperand operand;
      try {
        operand = filter.getExpression().accept(new ExpressionVisitorImpl(complexValue, null, edm));
      } catch (final ExpressionVisitException e) {
        throw new ODataApplicationException("Error in filter evaluation.",
            HttpStatusCode.INTERNAL_SERVER_ERROR.getStatusCode(), Locale.ROOT, e);
      }
      final Object filterResult = operand.asTypedOperand().getValue();
      if (Boolean.TRUE.equals(filterResult)) {
        result.add(value);
      }
    }
    return result;
  }
```

## Self-review

**Spec coverage.** §13.2.2 item 9's evaluation → Tasks 1 (`$top`, `$skip`), 2 (`$count`), 3 (`$filter`, `$orderby` on complex collections), 4 (an explicit, narrowed refusal for the rest). Item 8 (`$compute`), the re-audit and the tier record are Wave 4, for the reasons stated at the top. Item 5 and the MUSTs were closed in Waves 1 and 2.

**Type consistency.** `applySelectOptions(SelectOption, EntityCollection)` and `applySelectOptions(SelectOption, Entity)` are defined in Task 1 and used by the processor there. `applyToValue(SelectItem, Property)` is defined in Task 1 and extended in Tasks 2 and 3. `filterComplexValues(List<Object>, FilterOption, Edm)` and `orderComplexValues` are defined in Task 3. `isPrimitiveCollectionItem(SelectItem)` is defined in Task 4 on `TechnicalProcessor`, a different class from the handler, and deliberately not shared.

**Known soft spots, stated rather than hidden.** Task 1's wiring must reach both the collection and single-entity read paths; the step says to locate both. Task 2's count annotation spelling must be confirmed against the serializer rather than assumed. Task 3 passes `null` as the `UriInfoResource` to `ExpressionVisitorImpl` and says what to do if that is rejected, and its `orderComplexValues` deliberately reuses `OrderByHandler`'s comparison instead of inventing one. Task 4's test may find the parser refusing `$it` before the processor does; the step says to assert what actually happens and record why.
