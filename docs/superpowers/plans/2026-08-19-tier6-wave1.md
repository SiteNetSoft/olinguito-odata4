# Tier 6 Wave 1 Implementation Plan — CSDL JSON metadata (OLINGO-1300) + writer conformance + PR#11

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Olinguito read and write conformant CSDL JSON metadata on both sides of the wire. The server's JSON `$metadata` writer (`MetadataDocumentJsonSerializer`) is corrected to the OASIS representation so a conformant client can read it; `lib/server-core-ext` gains a `MetadataJsonParser` that produces the same `SchemaBasedEdmProvider` the XML `MetadataParser` produces, sharing one reference/core-vocabulary loader with it; the XML parser's version gate is widened to accept a `4.01` document; the client gains a CSDL JSON deserializer that produces the same `XMLMetadata`/`CsdlSchema` graph as the XML path, a `JSONMetadataRequest`, a `default RetrieveRequestFactory.getJSONMetadataRequest(String)` and a `Configuration` metadata-format switch that still defaults to XML; and the wrong `Nullable` default the XML parser applies to operation return types, parameters and terms (the PR#11 family) is fixed. XML metadata output stays byte-identical, and a client that expresses no format preference still gets XML.

**Architecture:** Four seams.
(1) **Server writer** — `lib/server-core/.../serializer/json/MetadataDocumentJsonSerializer.java` walks the `Edm` and writes CSDL JSON with a Jackson `JsonGenerator`. It deviates from [OData-CSDLJSON] in ways that make the document unreadable by a conformant parser: no document-level `$EntityContainer`; container inheritance under a nested `Extending` object; enum member values as strings; type-definition facets as strings while property facets are numbers; `$IsFlags`/`$IsBound` always written; `$Version` hard-coded `"4.01"`; entity sets missing the mandatory `$Collection`; `$OnDelete` written as an `OnDelete` object with an `Action` member; one `$ReferentialConstraint` object per constraint (duplicate member names); `$Kind` `"DEFINITION"` on type definitions; `$EntitySet` on imports prefixed with the schema alias; `$Kind` on entity sets, singletons and imports, which §13.2/§13.3/§13.5/§13.6 do not define; `$Type: "Edm.String"` on string properties, which §7.1 says SHOULD be omitted; constant expressions wrapped in `$Binary`/`$Date`/`$Int`/… member names that exist only in CSDL **XML**, and a record's type in a `$Type` member instead of the `@type` control information; and — the load-bearing one — `$Nullable` written with **XML** polarity (emitted only when `false`), while CSDL JSON defaults `$Nullable` to **false**, so every nullable property round-trips as non-nullable. Tasks 1–3 correct all of these; the changes are confined to the writer and its own test.
(2) **Server parser** — `lib/server-core-ext` has `MetadataParser` (StAX + an anonymous `ElementReader` visitor) producing `SchemaBasedEdmProvider`, plus its reference-resolution block (`loadReferencesSchemas`, `loadCoreVocabulary`, `loadLocalVocabularySchema`, `isCoreVocabulary`, `fixXmlBase`, `globalReferenceMap`). That block is extracted into a package-private `ReferenceLoader` collaborator parameterised by a `ProviderFactory` so the new `MetadataJsonParser` resolves `$Reference` exactly as the XML parser resolves `edmx:Reference`, including the local core vocabularies (which are XML resources — the JSON parser sniffs the first non-whitespace character of a referenced document and delegates XML documents to an internal `MetadataParser` sharing the same `globalReferenceMap`). The StAX visitor itself is not shared; the JSON parser is a Jackson `ObjectNode` walk with JSON defaults and JSON member names.
(3) **Client reader** — `ClientODataDeserializerImpl.toMetadata` is Jackson-XML only and `AbstractMetadataRequestImpl` hard-codes `Accept`/`Content-Type` to `application/xml` and no-ops the setters. A new package-private CSDL JSON parser in `lib/client-core/.../core/edm/xml/` builds plain `CsdlSchema` graphs and a `ClientCsdlJsonMetadata implements XMLMetadata`, reached through a new `default ClientODataDeserializer.toJSONMetadata(InputStream)`; `ODataReaderImpl.readMetadata(Map<String,CsdlSchema>)` and all `Edm` construction are reused unchanged.
(4) **Client request wiring** — `AbstractMetadataRequestImpl` gains a format-aware constructor (the existing one delegates with `APPLICATION_XML`, so `XMLMetadataRequestImpl` is byte-identical), `client-api` gains `JSONMetadataRequest` and `default RetrieveRequestFactory.getJSONMetadataRequest(String)`, and `Configuration` gains `default getMetadataFormat()`/`setMetadataFormat(ContentType)` (XML default) that `EdmMetadataRequestImpl` honors when choosing between the XML and the JSON metadata request.

**Tech Stack:** Java 17, Maven; modules `lib/server-core`, `lib/server-core-ext`, `lib/client-api`, `lib/client-core`, `fit`, plus `docs/`. Jackson (`jackson-core`, `jackson-databind`) is already a dependency of `server-core`, `server-core-ext` (transitively through `odata-server-core`) and `client-core`. No new dependencies, no new modules.

**Spec:** `docs/superpowers/specs/2026-08-19-tier6-design.md` (Feature 1, sections 1a–1d, plus "Milestone structure" and "Conformance summary / Recorded deviations") and `docs/superpowers/specs/2026-08-19-tier6-citations.md` (section 1, subsections 1.1–1.15, and the **Gaps** entries for Feature 1). Every JSON member name, default and MUST/MAY in this plan is quoted from the citations file; where the citations file records a gap, the choice made here is named as a decision, never as a spec rule.

### Task 2: Correct the CSDL JSON facet and default polarity — `$Nullable`, `$Type`, enum values, type-definition facets, `$OnDelete`, `$ReferentialConstraint`

Conformance targets (citations §1.6 §7.2.1, §1.7 §8.2/§8.5/§8.6, §1.9 §10.2/§10.3, §1.10 §11, §1.11 §12.5):
- `$Nullable`: "The value of $Nullable is one of the Boolean literals true or false. **Absence of the member means false.**" (the XML attribute defaults to true — opposite polarity)
- Enum members: "the object member name is the enumeration member name and the object member value is the enumeration member value", and "Each member MUST specify an associated **numeric** value".
- `$IsFlags`/`$IsBound`: "Absence of the member means false", plus §2.2 "In general, all members that have a default value SHOULD be omitted if they have the default value."
- Type definition: "The type definition object MUST contain the member $Kind with a string value of **TypeDefinition**"; its facets are the §7.2 facets, i.e. `$MaxLength`/`$Precision`/`$Scale` are numbers and `$SRID` is "a string containing a number or the symbolic value variable".
- `$ReferentialConstraint`: "The value of $ReferentialConstraint is an object with **one member per referential constraint**."
- `$OnDelete`: "The value of $OnDelete is a string with one of the values Cascade, None, SetNull, or SetDefault." / "Annotations for $OnDelete are prefixed with $OnDelete."
- `$Type` on a structural property (§7.1): "Absence of the $Type member means the type is Edm.String. This member SHOULD be omitted for string properties to reduce document size." — a SHOULD with no semantic cost, because the same clause makes `Edm.String` the default a reader applies (§7.1's Example 16 is `"Units": { "$Collection": true }`, a collection of strings written without `$Type`). The omission is implemented for **structural properties only**: §12.8 and §12.9 state the same `Edm.String` default for return types and parameters but carry no SHOULD-omit sentence, so those keep writing `$Type`.

  private void readDocument(final ObjectNode document, final SchemaBasedEdmProvider provider, final String path)
      throws CsdlJsonParseException {
    // Section 4: "This document object MUST contain the member $Version" whose value "is a string
    // containing either 4.0 or 4.01".
    final JsonNode version = document.get(VERSION);
    if (version == null || !version.isTextual()) {
      throw new CsdlJsonParseException(child(path, VERSION), "the document object must carry $Version");
    }
    if (!ODataServiceVersion.V40.toString().equals(version.asText())
        && !ODataServiceVersion.V401.toString().equals(version.asText())) {
      throw new CsdlJsonParseException(child(path, VERSION), "only 4.0 and 4.01 are valid CSDL JSON versions");
    }
    if (document.has(REFERENCES)) {
      readReferences(objectNode(document, REFERENCES, path), provider, child(path, REFERENCES));
    }
    final Iterator<Map.Entry<String, JsonNode>> members = document.fields();
    while (members.hasNext()) {
      final Map.Entry<String, JsonNode> member = members.next();
      if (member.getKey().startsWith(DOLLAR) || member.getKey().startsWith("@")) {
        continue; // $Version, $EntityContainer, $Reference and document annotations
      }
      provider.addSchema(readSchema(member.getKey(), objectNode(member, path), child(path, member.getKey())));
    }
  }

  private List<CsdlPropertyRef> readKey(final ArrayNode key, final String path) throws CsdlJsonParseException {
    final List<CsdlPropertyRef> refs = new ArrayList<>();
    for (int i = 0; i < key.size(); i++) {
      final JsonNode item = key.get(i);
      if (item.isTextual()) {
        // Section 6.5: "Key properties without a key alias are represented as strings containing the
        // property name."
        refs.add(new CsdlPropertyRef().setName(item.asText()));
      } else if (item.isObject() && item.size() == 1) {
        // "Key properties with a key alias are represented as objects with one member whose name is
        // the key alias and whose value is a string containing the path to the property."
        final Map.Entry<String, JsonNode> alias = item.fields().next();
        refs.add(new CsdlPropertyRef().setAlias(alias.getKey()).setName(alias.getValue().asText()));
      } else {
        throw new CsdlJsonParseException(path + "[" + i + "]",
            "a key item is either a property name or a single-member alias object");
      }
    }
    return refs;
  }

**Annotation member grammar (citations §1.13 §14.2).** "An annotation is represented as a member whose name consists of an at (@) character, followed by the qualified name of a term, optionally followed by a hash (#) and a qualifier." A *targeted* annotation member is `<target>@<term>[#<qualifier>]`, where `<target>` is the enum member name, the property name inside a record, `$OnDelete`, the dependent property of a referential constraint, or the annotation itself when the annotation is annotated. Parsing rule used everywhere: split the member name at the **first** `@`; the part before it is the target prefix (empty means "this object"), the part after it is `term[#qualifier]`. `parseAnnotations(false)` (the default, matching `MetadataParser`) skips every `@` member without inspecting it.

**Expression mapping (citations §1.14, §1.15, and the Gaps entries).** CSDL JSON has **no** `$Binary`/`$Date`/`$DateTimeOffset`/`$Decimal`/`$Duration`/`$EnumMember`/`$Float`/`$Guid`/`$Int`/`$String`/`$TimeOfDay` members — those are CSDL XML element names — and **no** `$Record` member and no `$Type` on a record. **Type recovery for constants (recorded deviation).** A conformant CSDL JSON document carries no per-value type marker: §14.3 represents a `Binary`, a `Date` and a `String` constant identically, as JSON strings. ## Dropped / Re-scoped

- **PR#11 is re-scoped: the navigation-property `Nullable` default was already fixed years ago; three siblings of the same defect were not.** Evidence: `MetadataParser.java:985` (navigation property) and `:1034` (structural property) already read `attr(element, "Nullable") == null ? "true" : ...`, and `git blame` dates that line to `e31e303c9f` (Ramesh Reddy, 2016-07-22). The surviving defect is at `MetadataParser.java:500` (`readReturnType`), `:529` (`readParameter`) and `:597` (`readTerm`), all still `Boolean.parseBoolean(attr(element, "Nullable"))`, i.e. **false** when the attribute is absent, while `CsdlReturnType.java:37`, `CsdlParameter.java:41` and `CsdlTerm.java:42` all initialise `nullable = true`. Task 4 fixes those three and pins all five.
- **Recorded deviation (new): CSDL JSON carries no per-value type marker, so a constant expression's type is recovered from the term's declared type, else `String`.** Evidence: citations §14.3 renders `Binary`, `Date`, `DateTimeOffset`, `Duration`, `EnumMember`, `Guid`, `String` and `TimeOfDay` constants identically, as JSON strings, and the Gaps entry confirms there are no `$Binary`/`$Date`/`$Int`/… member names to disambiguate them. Task 3 makes the writer conformant (bare JSON values) and Task 7's parser recovers the four shapes JSON does distinguish — `Bool`, `Int`, `Float`, `String`. The round trip therefore compares constant **values** exactly and normalizes only the type tag; `MetadataJsonRoundTripTest#constantAnnotationValuesSurviveTheRoundTrip` states the normalization in one small `jsonShape(...)` method rather than weakening any assertion. This is a property of the format the spec chose, and it is to be added to the design spec's Recorded-deviations list in Task 10.
- **`$Has` and `$In` (§14.4.2) are parse errors, not silent drops.** Evidence: `CsdlLogicalOrComparisonExpression.LogicalOrComparisonExpressionType` declares `And, Or, Not, Eq, Ne, Gt, Ge, Lt, Le` and nothing else, so there is no Csdl model to build; adding two enum constants to a public API enum in `commons-api` is not additive for exhaustive switches and is out of this wave's scope. The parser raises a `CsdlJsonParseException` naming the member.
- **The client and the server do not share one CSDL JSON parser.** Evidence: `lib/commons-api/pom.xml` and `lib/commons-core/pom.xml` declare no Jackson dependency (only `client-core`, `server-core` and their dependents do), so the only shared home for a common parser would require adding Jackson to `commons-*` and to every OSGi bundle that consumes it; and `client-core` must not depend on `server-core-ext`. The two readers therefore share the member→setter tables in this plan (Tasks 5–7 and Task 8 use the same rows) rather than code. This is the same split the codebase already lives with for XML: `MetadataParser` (StAX) and `ClientCsdl*` (Jackson-XML) parse the same format twice.
- **The client's JSON metadata request does not follow `$Reference` documents.** Evidence: `XMLMetadataRequestImpl.processReferences` (lines 86–151) implements recursive reference following with cycle detection for the XML path only, driven by `XMLMetadata#getReferences`. The JSON request returns the primary document's schemas; a service whose vocabularies live behind `$Reference` will produce an `Edm` without them. Recorded in the guide's "Known limitations"; the server-side parser does follow references (Task 5).
- **The hand-written `trippin.json` twin is replaced by two stronger fixtures.** A 461-line hand-maintained JSON copy of `trippin.xml` would drift the moment either file changed and would prove only that someone transcribed correctly. Instead: `MetadataJsonRoundTripTest` (Task 7) parses `trippin.xml`, serializes it through the corrected writer and re-parses the JSON, comparing the two `Csdl*` graphs — which is the XML↔JSON equivalence the design asks for *and* the writer→parser round trip; and `csdl-json-conformant.json` (Task 5) is a small, hand-written, deliberately foreign document (alias-qualified names, omitted `$Type`, numeric enum values, `$Key` alias objects, flat `$Extends`) that no Olinguito writer produces, proving the parser is not just reading its own output.
- **`$Version` changes from `"4.01"` to `"4.0"` on the wire.** Not a regression: `ServiceMetadataImpl.getDataServiceVersion()` returns `ODataServiceVersion.V40` (`ServiceMetadataImpl.java:79–81`), `MetadataDocumentXmlSerializer` writes `Version="4.0"` (line 179) and `ODataHandlerImpl` sends `OData-Version: 4.0` (line 158). The document previously claimed a version the service does not serve. §4 accepts both values and the new parser accepts both.
- **The `IEEE754Compatible` and `metadata` media-type parameters of §2.1 are not implemented for `$metadata`.** The writer emits numbers as JSON numbers (the `IEEE754Compatible=false` behavior, which is the default) and always writes the same amount of control information. Recorded in the guide's "Known limitations".

**Spec coverage.** Every member name, default and strength in this plan is quoted from `docs/superpowers/specs/2026-08-19-tier6-citations.md` §1.1–§1.15, never from memory. SHOULD-level honored: defaults are omitted (§2.2) for `$IsFlags`, `$IsBound`, `$Abstract`, `$OpenType`, `$HasStream`, `$Nullable`, `$ContainsTarget`, and `$Type` is omitted for `Edm.String` properties (§7.1, Task 2) with the reader's `Edm.String` default pinned as its counterpart (Task 5's `absentTypeMeansEdmString`). Protocol §11.1.2's "If a request for metadata does not specify a format preference … the XML representation MUST be returned" is pinned twice on the client (Task 9's `xmlMetadataRequestStillForcesApplicationXml`, Task 10's `defaultMetadataFormatIsStillXml`).
