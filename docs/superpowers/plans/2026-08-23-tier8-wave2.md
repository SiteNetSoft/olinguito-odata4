# Tier 8 Wave 2 — Nested Options in `$select`

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `$select` the parenthesized nested-option grammar [OData-Protocol] §11.2.5.1 defines, and honor `$select` nested within `$select` — §13.2.2 item 5, the level's remaining MUST.

**Architecture:** Three layers. `SelectItem` (server-api) gains the sub-option accessors `ExpandItem` already carries; `SelectParser` gains an option loop mirroring `ExpandParser`'s, enforcing the spec's per-kind option split; and `ExpandSelectHelper` learns to read a nested `$select` when computing selected sub-paths, which is what makes the projection actually happen.

**Tech Stack:** Java 17, Maven, JUnit 5 in `lib/**`, JUnit 4 via the vintage engine in `fit/`.

**Spec:** `docs/superpowers/specs/2026-08-22-tier8-design.md` (citations: `docs/superpowers/specs/2026-08-22-tier8-citations.md`)

## Scope, and what moved to Wave 3

The design's Wave 2 bundled nested options with `$compute`, and pre-authorized splitting `$compute` out "if it grows". It has: `$compute` needs a `SystemQueryOptionKind` constant, a parser, accessors on `UriInfo`/`SelectItem`/`ExpandItem`, an evaluator producing dynamic properties, and an evaluation order ahead of `$select`/`$filter`/`$orderby`. That is a wave.

A second split, discovered while planning: **evaluating** `$filter`/`$orderby`/`$count`/`$search`/`$skip`/`$top` on a *selected collection-valued property* has no existing machinery — `ExpandSystemQueryOptionHandler` applies those to expanded **entity** collections, whereas these apply to a primitive or complex collection **property value** on each entity. That is item 9, a SHOULD.

So:

- **This wave (2):** the API, the grammar with per-kind validation, and nested `$select` projection end to end — item 5, the MUST. The collection-valued options **parse** and then answer **501**, which [OData-Protocol] §13.1.2 item 2 explicitly sanctions (*"MUST return 501 for unsupported functionality"*) and which is honest: a parsed option that silently did nothing would be the exact "parsed then dropped" failure this project's audit keeps finding.
- **Wave 3:** evaluate those collection options (item 9), `$compute` (item 8), then the §13.2.2/§13.1.2 re-audit and the tier record.

## Global Constraints

- **The spec's option split is the parser's split.** [OData-Protocol] §11.2.5.1: *"Allowed system query options are $select and $compute for complex properties, plus $filter, $search, $count, $orderby, $skip, and $top for collection-valued properties."* Per [OData-ABNF], a **navigation** property in `$select` takes no options and a plain primitive takes none — `selectProperty` gives the bracketed form only to `primitiveColProperty` (the six) and to `selectPath`, which is complex-only. The design text says "complex or navigation path"; the ABNF and the prose are narrower, and they win.
- **`$compute` is not accepted in this wave.** It is part of `selectOption` in the ABNF, but there is no `$compute` anywhere yet; parsing it here would mean accepting a name the rest of the system cannot honor. Wave 3 adds it to the same loop.
- **The existing `/`-path nesting must keep working** — `$select=PropertyComp/PropertyInt16` is unaffected by this wave.
- **A property must not carry options twice**, and must not carry both select options and expand options ([OData-Protocol] §11.2.5.1). Enforced for its two clear cases (design D4).

Add the two helpers. `parseSelectOptions` mirrors `ExpandParser`'s dispatch loop (`ExpandParser.java:280-320`) — copy its structure, including `ParserHelper.requireNext(tokenizer, TokenKind.EQ)` after each option name and `TokenKind.SEMI` between options:

```java
  /**
   * Parses the parenthesized, semicolon-separated option group a selected property may carry
   * ([OData-Protocol] 11.2.5.1). Which options are admissible depends on the property:
   * $select on a complex property, and the collection options on a collection-valued one.
   * @param allowNested whether $select may appear, i.e. whether the property is complex
   */
  private void parseSelectOptions(UriTokenizer tokenizer, final EdmStructuredType referencedType,
      final EdmProperty property, final boolean allowNested)
      throws UriParserException, UriValidationException {
    if (!tokenizer.next(TokenKind.OPEN)) {
      return;
    }
    do {
      if (allowNested && tokenizer.next(TokenKind.SELECT)) {
        ParserHelper.requireNext(tokenizer, TokenKind.EQ);
        item.setSelectOption(new SelectParser(edm, odata).parse(tokenizer,
            (EdmStructuredType) property.getType(), property.isCollection()));
      } else if (property.isCollection() && tokenizer.next(TokenKind.FILTER)) {
        ParserHelper.requireNext(tokenizer, TokenKind.EQ);
        item.setFilterOption(new FilterParser(edm, odata).parse(tokenizer,
            property.getType() instanceof EdmStructuredType structured ? structured : referencedType,
            null, null));
      } else {
        throw new UriParserSemanticException("Not allowed as select option: " + tokenizer.getText(),
            UriParserSemanticException.MessageKeys.UNKNOWN_PART, tokenizer.getText());
      }
    } while (tokenizer.next(TokenKind.SEMI));
    ParserHelper.requireNext(tokenizer, TokenKind.CLOSE);
  }

  private void rejectOptionGroup(UriTokenizer tokenizer, final String name) throws UriParserException {
    if (tokenizer.next(TokenKind.OPEN)) {
      throw new UriParserSemanticException("Options are not allowed on this select item: " + name,
          UriParserSemanticException.MessageKeys.UNKNOWN_PART, name);
    }
  }
```

The sketch shows `$select` and `$filter`; add `$search`, `$count`, `$orderby`, `$skip` and `$top` branches in the same shape, copying each from the corresponding branch of `ExpandParser.parseExpandOptions` (`$orderby` → `new OrderByParser(edm, odata).parse(...)`; `$search` → `new SearchParser().parse(tokenizer)`; `$skip`/`$top` → `ParserHelper.requireNext(tokenizer, TokenKind.IntegerValue)` then `ParserHelper.parseNonNegativeInteger`; `$count` → `TokenKind.BooleanValue` into a `CountOptionImpl`). Do **not** add a `$compute` branch — Wave 3 does.
